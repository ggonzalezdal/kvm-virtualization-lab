**# Phase 5 --- Firewall & Security**

**## 1. Objective**

The first part of Phase 5 focused on protecting ****Alpine-Lab-01 itself****

using a stateful `iptables` firewall.

At this checkpoint, the router provides:

-   Routing between the isolated LAN and the external libvirt network

-   NAT/MASQUERADE for the isolated LAN

-   DHCP

-   DNS

-   SSH

-   ICMP Echo Request from the trusted LAN

-   Stateful connection tracking

-   Persistent firewall rules

The `INPUT` firewall is functional and persisted.

The second part of this checkpoint extended the same stateful-firewall

principles to traffic travelling ****through**** Alpine-Lab-01. The

`FORWARD` chain now uses a default `DROP` policy with explicit rules for

LAN-initiated traffic and return traffic.

**## 3. Current Firewall Policies**

The current filter policies are:

``` text

INPUT    DROP

FORWARD  DROP

OUTPUT   ACCEPT

```

This means:

-   `INPUT DROP`: traffic addressed to Alpine-Lab-01 is denied unless

    explicitly permitted.

-   `FORWARD DROP`: routed traffic through Alpine-Lab-01 is denied

    unless explicitly permitted.

-   `OUTPUT ACCEPT`: traffic generated by Alpine-Lab-01 is currently

    unrestricted.

The distinction between the three chains is fundamental:

``` text

Traffic TO the router       -> INPUT

Traffic FROM the router     -> OUTPUT

Traffic THROUGH the router  -> FORWARD

```

Example:

``` text

Alpine-02 -> SSH -> Alpine-01

                    |

                  INPUT

```

while:

``` text

Alpine-02 -> Alpine-01 -> Internet

                    |

                  FORWARD

```

**## 5. Stateful Firewall and conntrack**

Linux Netfilter can track the state of network exchanges using

connection tracking (`conntrack`).

Important states introduced during this phase:

``` text

NEW

ESTABLISHED

RELATED

```

`NEW` represents traffic beginning a new tracked exchange.

`ESTABLISHED` represents subsequent traffic belonging to an exchange

that Netfilter already recognizes.

`RELATED` represents traffic associated with an existing tracked

connection.

The general rule:

``` bash

-m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

```

allows traffic belonging to already recognized connections.

This is the basis of a ****stateful firewall****.

**## 6. ICMP and INPUT vs FORWARD**

ICMP stands for ****Internet Control Message Protocol****.

It is used for network control and diagnostic messages. `ping` uses ICMP

Echo Request and Echo Reply.

Initially:

``` bash

ping -c 3 10.10.10.1

```

from Alpine-Lab-02 failed.

However:

``` bash

ping -c 3 8.8.8.8

```

worked.

This demonstrated the difference between `INPUT` and `FORWARD`.

Ping to the router:

``` text

Alpine-02

    |

    | ICMP Echo Request

    v

10.10.10.1

    |

  INPUT

    |

  DROP

```

Ping through the router:

``` text

Alpine-02

    |

    | ICMP Echo Request

    v

Alpine-01

    |

 FORWARD

    |

 ACCEPT

    v

8.8.8.8

```

An explicit rule was added for Echo Requests arriving from the trusted

LAN:

``` bash

-A INPUT -i eth1 -p icmp --icmp-type 8 -j ACCEPT

```

Afterward, pinging `10.10.10.1` worked successfully.

**## 7. ICMP + conntrack Experiment**

A temporary experiment was performed to observe connection tracking

directly.

Two temporary rules were inserted before the generic

`RELATED,ESTABLISHED` rule:

``` text

ICMP echo-request + NEW          -> ACCEPT

ICMP echo-request + ESTABLISHED  -> ACCEPT

```

Then:

``` bash

ping -c 3 10.10.10.1

```

was executed.

The counters showed:

``` text

NEW           1 packet

ESTABLISHED   2 packets

```

This demonstrated that conntrack treated the first Echo Request as the

beginning of the tracked exchange and subsequent requests as part of the

established exchange.

The temporary diagnostic rules were removed afterward.

The permanent ICMP rule remains:

``` bash

-A INPUT -i eth1 -p icmp --icmp-type 8 -j ACCEPT

```

**## 8. DHCP Firewall Rule**

DHCP stands for ****Dynamic Host Configuration Protocol****.

It automatically provides network configuration such as:

-   IP address

-   Subnet mask

-   Default gateway

-   DNS server

-   Lease information

In this lab, Alpine-Lab-01 provides DHCP through `dnsmasq`.

DHCP clients communicate primarily using UDP ports 67 and 68.

With `INPUT DROP`, DHCP initially failed because requests reached `eth1`

but were dropped before `dnsmasq` could process them.

The following rule fixed the problem:

``` bash

-A INPUT -i eth1 -p udp --dport 67 -j ACCEPT

```

This permits DHCP requests arriving from the isolated LAN.

**## 10. Loopback Firewall Problem**

A separate DNS issue occurred on Alpine-Lab-01 itself.

Its `/etc/resolv.conf` contained:

``` text

search lab.local

nameserver 10.10.10.1

```

However:

``` bash

nslookup alpine-lab-02

```

timed out.

A packet capture was performed:

``` bash

sudo tcpdump -ni lo 'port 53'

```

It showed DNS requests such as:

``` text

10.10.10.1:\<client-port> -> 10.10.10.1:53

```

travelling through `lo`.

The existing DNS firewall rule only permitted packets arriving through

`eth1`. Therefore local DNS traffic did not match the rule and

eventually hit `INPUT DROP`.

The correct general solution was to permit loopback traffic:

``` bash

-A INPUT -i lo -j ACCEPT

```

After adding this rule:

``` bash

nslookup alpine-lab-02

```

worked correctly from Alpine-Lab-01.

This demonstrates why a default-deny host firewall normally needs an

explicit loopback rule.

**## 11. Local DNS / 127.0.0.1 Problem**

Another name-resolution problem was discovered when Alpine-Lab-02

executed:

``` bash

nslookup alpine-lab-01

```

and received:

``` text

127.0.0.1

```

instead of:

``` text

10.10.10.1

```

The cause was Alpine-Lab-01's `/etc/hosts`.

It contained:

``` text

127.0.0.1 alpine-lab-01.my.domain alpine-lab-01 localhost.localdomain localhost

```

At the same time, `dnsmasq` was configured with:

``` text

expand-hosts

```

As a result, the local hostname information was exposed through DNS.

This produced an important semantic problem for remote clients:

`127.0.0.1` always means ****this host****.

Therefore, when Alpine-Lab-02 resolved:

``` text

alpine-lab-01 -> 127.0.0.1

```

and executed:

``` bash

ssh airgon@alpine-lab-01

```

it actually connected back to Alpine-Lab-02 itself.

The problem was confirmed using:

``` bash

ssh -v airgon@alpine-lab-01

```

which showed:

``` text

Connecting to alpine-lab-01 [127.0.0.1] port 22.

```

**## 13. SSH Host-Key Warning**

After fixing DNS, SSH produced:

``` text

WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

```

This occurred because the hostname `alpine-lab-01` had previously

resolved incorrectly to `127.0.0.1`.

Alpine-Lab-02 had therefore associated the hostname with the wrong SSH

host identity.

The incorrect hostname entries were removed:

``` bash

ssh-keygen -R alpine-lab-01

ssh-keygen -R alpine-lab-01.lab.local

```

The new ED25519 fingerprint presented over the network was:

``` text

SHA256:RgJxw2RXzvc2VMLjZrrxyfGCsH8ZQvBVtXsQIhCHV88

```

Instead of blindly accepting the key, the actual host key was verified

directly on Alpine-Lab-01:

``` bash

sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

```

Result:

``` text

256 SHA256:RgJxw2RXzvc2VMLjZrrxyfGCsH8ZQvBVtXsQIhCHV88 root@alpine-lab-01 (ED25519)

```

The fingerprints matched exactly.

This demonstrates an important SSH security principle:

> A changed SSH host key should not automatically be accepted. The new

> fingerprint should first be verified through a trusted path.

A later verbose SSH test confirmed successful hostname resolution,

host-key verification, password authentication, PTY allocation, and

interactive shell startup.

**## 16. Stateful FORWARD Firewall**

Before hardening, the `FORWARD` chain had no explicit rules and used:

``` text

FORWARD ACCEPT

```



**## 17. Building the Stateful FORWARD Rules**

The first explicit forwarding rule permits traffic belonging to

connections already known by conntrack:

``` bash

sudo iptables -A FORWARD \\

    -m conntrack --ctstate RELATED,ESTABLISHED \\

    -j ACCEPT

```

The second rule permits the trusted LAN to initiate new traffic toward

the external interface:

``` bash

sudo iptables -A FORWARD \\

    -i eth1 -o eth0 \\

    -s 10.10.10.0/24 \\

    -m conntrack --ctstate NEW \\

    -j ACCEPT

```

At this stage the default policy was deliberately left at `ACCEPT` as a

temporary safety net.

``` text

LAN -> WAN

NEW                         ACCEPT

Return / ongoing traffic

RELATED,ESTABLISHED         ACCEPT

Anything not matching

default policy              ACCEPT (temporary safety net)

```

**## 19. DNS and the FORWARD Chain**

An important distinction was observed when using:

``` bash

nslookup google.com

```

from Alpine-Lab-02.

The client uses:

``` text

nameserver 10.10.10.1

```

Therefore the client's DNS query is addressed to Alpine-Lab-01 itself

and traverses `INPUT`. If dnsmasq needs an upstream answer, dnsmasq

generates that query itself and it traverses `OUTPUT`.

``` text

Alpine-Lab-02 -> DNS -> INPUT -> dnsmasq

                                  |

                                OUTPUT

                                  |

                                  v

                           upstream DNS

```

This DNS proxy path does ****not**** traverse `FORWARD`.

**## 20. Removing the FORWARD Safety Net**

After confirming that the explicit rules handled the outbound flow, the

default policy was changed:

``` bash

sudo iptables -P FORWARD DROP

```

The forwarding firewall became:

``` text

FORWARD DROP

|

+-- RELATED,ESTABLISHED                         ACCEPT

|

+-- eth1 -> eth0

    source 10.10.10.0/24

    NEW                                         ACCEPT

```

The resulting security model is:

``` text

LAN -> WAN NEW                    ACCEPT

WAN -> LAN ESTABLISHED/RELATED    ACCEPT

WAN -> LAN unsolicited NEW        DROP

```

**## 23. Longest-Prefix Matching**

To force one test destination through Alpine-Lab-01, a temporary host

route was added on Linux Mint:

``` bash

sudo ip route add 10.10.10.2/32 \\

    via 192.168.122.252 dev virbr0

```

Linux Mint then had both:

``` text

10.10.10.0/24  -> virbr10

10.10.10.2/32  -> via 192.168.122.252

```

Linux routing uses ****longest-prefix matching****. Both routes match

`10.10.10.2`, but `/32` is more specific than `/24`, so `/32` wins:

``` text

/32 > /24 > /0

```

General rule:

> When several routes match a destination, Linux selects the route with

> the longest matching network prefix.

The test path therefore became:

``` text

Linux Mint

192.168.122.1

      |

      v

Alpine-Lab-01 eth0

192.168.122.252

      |

   FORWARD

      |

    eth1

      |

      v

Alpine-Lab-02

10.10.10.2

```

## 25. Firewall Logging

Firewall logging was added before the default `DROP` decisions.

For `INPUT`:

```bash
-A INPUT -m limit --limit 5/min --limit-burst 10 \
    -j LOG --log-prefix "IPTABLES-DROP: "
```

For `FORWARD`:

```bash
-A FORWARD -m limit --limit 5/min --limit-burst 10 \
    -j LOG --log-prefix "FORWARD-DROP: "
```

The rate limit prevents a flood of denied packets from overwhelming the log.

On Alpine Linux, BusyBox `syslogd` and `klogd` were used:

```text
/sbin/syslogd -t -n
/sbin/klogd -n
```

Firewall messages were intentionally kept in:

```text
/var/log/messages
```

Example blocked TCP connection from Alpine-Lab-02:

```text
IPTABLES-DROP: IN=eth1 SRC=10.10.10.2 DST=10.10.10.1
PROTO=TCP SPT=35307 DPT=9999 SYN
```

The repeated SYN packets used the same source port because they were
retransmissions from the same TCP connection attempt.

## 26. Nmap: open, closed, and filtered

`nmap` was installed on Alpine-Lab-02 and used to observe how firewall
behavior appears from a client.

A SYN scan with:

```bash
sudo nmap -Pn -sS -p 22,8888,9999 10.10.10.1
```

demonstrated three useful states:

```text
open       a service is listening and reachable
closed     the host is reachable but no service accepts the connection
filtered   packet filtering prevents Nmap from determining the port state
```

Port 22 was `open`.

A temporary rule allowing TCP/8888 while no service listened on the port made
8888 appear `closed`, because the TCP stack could answer with RST.

Port 9999 remained `filtered` under `DROP`.

A temporary `REJECT --reject-with tcp-reset` rule for TCP/9999 made the same
port appear `closed` immediately. This demonstrated the practical difference:

```text
DROP       silently discard; scanner waits/retries; often "filtered"
REJECT     actively refuse; scanner receives an immediate answer
```

All temporary test rules were removed afterward.

## 27. DNS over UDP and TCP

The original DNS firewall rule permitted only UDP/53.

Testing showed:

```text
UDP/53     open
TCP/53     filtered
```

Because `dnsmasq` listens on both transports, TCP DNS was explicitly allowed
for trusted LAN clients:

```bash
-A INPUT -i eth1 -s 10.10.10.0/24 -p tcp \
    --dport 53 -m conntrack --ctstate NEW -j ACCEPT
```

Afterward both UDP/53 and TCP/53 were reachable.

This reinforced an important distinction:

> A service listening on a socket does not mean the firewall makes that
> service reachable.

## 28. Source and Interface Hardening

The service rules were tightened so that trusted services are not merely
identified by destination port.

Final SSH rule:

```bash
-A INPUT -s 10.10.10.0/24 -i eth1 -p tcp \
    --dport 22 -m conntrack --ctstate NEW -j ACCEPT
```

Final DNS rules:

```bash
-A INPUT -s 10.10.10.0/24 -i eth1 -p udp --dport 53 -j ACCEPT

-A INPUT -s 10.10.10.0/24 -i eth1 -p tcp \
    --dport 53 -m conntrack --ctstate NEW -j ACCEPT
```

Final ICMP rule:

```bash
-A INPUT -s 10.10.10.0/24 -i eth1 -p icmp --icmp-type 8 -j ACCEPT
```

The DHCP rule intentionally remains interface-restricted rather than
source-restricted:

```bash
-A INPUT -i eth1 -p udp --dport 67 -j ACCEPT
```

An initial DHCP client may legitimately send from `0.0.0.0` before it has
received a LAN address. Requiring `-s 10.10.10.0/24` would therefore interfere
with DHCP bootstrap. Here, `eth1` is the security boundary.

`INPUT` logging rule.

Alpine-Lab-01 showed strict reverse-path filtering:

```text
net.ipv4.conf.eth1.rp_filter = 1
net.ipv4.conf.all.rp_filter = 1
```

With strict `rp_filter`, Linux checks whether the source address is plausible
according to the routing table. Because the route back to `10.20.20.2` did not
use `eth1`, the packet was discarded before normal `INPUT` processing.

A temporary route was added:

```bash
sudo ip route add 10.20.20.0/24 dev eth1
```

The packet then became routing-plausible and reached the firewall, where it
was logged and dropped because `10.20.20.2` is outside the authorized
`10.10.10.0/24` source network.

This separated two concepts:

```text
rp_filter   Is this source plausible according to routing?
iptables    Is this source authorized by firewall policy?
```

The temporary address and route were removed after the experiment.

## 30. FORWARD Logging and Reverse-Direction Test

A rate-limited logging rule was appended to `FORWARD`:

```bash
sudo iptables -A FORWARD \
    -m limit --limit 5/min --limit-burst 10 \
    -j LOG --log-prefix "FORWARD-DROP: "
```

Linux Mint normally reaches `10.10.10.2` directly through `virbr10`, bypassing
Alpine-Lab-01. To force a controlled reverse-direction test through the router,
a temporary host route was used:

```bash
sudo ip route add 10.10.10.2/32 \
    via 192.168.122.252 dev virbr0
```

Then:

```bash
ping -c 3 10.10.10.2
```

failed as expected.

Alpine-Lab-01 logged all three Echo Requests:

```text
FORWARD-DROP: IN=eth0 OUT=eth1
SRC=192.168.122.1 DST=10.10.10.2
PROTO=ICMP TYPE=8
```

Counters changed by:

```text
FORWARD-DROP log     +3
FORWARD policy DROP  +3
```

This directly proved:

```text
LAN -> upstream NEW                  ACCEPT
upstream -> LAN unsolicited NEW      DROP
upstream -> LAN ESTABLISHED/RELATED  ACCEPT
```

The temporary `/32` route was removed immediately after the test.

## 31. NAT / MASQUERADE and conntrack

The NAT rule is:

```bash
-A POSTROUTING -s 10.10.10.0/24 -o eth0 -j MASQUERADE
```

For example, traffic originating from:

```text
10.10.10.2 -> 8.8.8.8
```

leaves Alpine-Lab-01 with its source translated to the current address of
`eth0`, `192.168.122.252`.

Conntrack remembers the translation so replies can be mapped back to the
original internal client.

A three-ping experiment illustrated the difference between filtering and NAT
counters:

```text
FORWARD NEW                  +1
FORWARD ESTABLISHED          +5
MASQUERADE                   +1
```

The six forwarded packets are filtered individually, but the NAT table
establishes the translation for the tracked flow on its first packet and
conntrack reuses that mapping for subsequent packets.

## 36. Key Lessons

### INPUT vs OUTPUT vs FORWARD

```text
Destination is the router:   INPUT
Generated by the router:     OUTPUT
Passing through the router:  FORWARD
```

### Default-deny firewalling

```text
INPUT    DROP
FORWARD  DROP
OUTPUT   ACCEPT
```

### Stateful filtering

`conntrack` lets Netfilter classify traffic as:

```text
NEW
ESTABLISHED
RELATED
```

This allows a client to initiate a permitted connection while return traffic
is accepted without creating broad reverse-direction rules.

### Service listening != service reachable

A daemon can listen on a socket while `iptables` makes that socket
unreachable. TCP/53 demonstrated this directly.

### DROP vs REJECT

```text
DROP     silent discard
REJECT   explicit refusal
```

This difference changes both client behavior and what tools such as Nmap
report.

### Interface and source restrictions are complementary

Rules such as:

```text
-i eth1 -s 10.10.10.0/24
```

express both where trusted traffic must arrive and which source network is
authorized.

### DHCP is special

A DHCP client may begin with source address `0.0.0.0`, so the DHCP rule uses
the trusted interface as its security boundary rather than requiring an
already-assigned `10.10.10.0/24` address.

### rp_filter and iptables solve different problems

```text
rp_filter   source routing plausibility
iptables    security authorization
```

A packet may be route-valid but still forbidden by firewall policy.

### DNS is not always FORWARD traffic

LAN clients query Alpine-Lab-01 itself:

```text
client -> INPUT -> dnsmasq
dnsmasq -> OUTPUT -> upstream DNS
```

### NAT is flow-oriented through conntrack

The NAT rule establishes a translation for a tracked flow. Conntrack then
reuses that mapping instead of independently choosing a new NAT translation
for every subsequent packet.

### Longest-prefix matching

```text
/32 > /24 > /0
```

The temporary `/32` route on Linux Mint allowed a controlled test to override
the normal directly connected `virbr10` route.

### Persistence must be tested, not assumed

Saving a configuration is not enough. Rebooting and verifying interfaces,
routing, forwarding, firewall rules, NAT, services, client connectivity, and
logging demonstrated that the router/firewall can actually recover.

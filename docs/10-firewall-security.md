- NAT/MASQUERADE for the isolated LAN
- DHCP
- DNS

## 3. Current Firewall Policies

The current filter policies are:

```text
INPUT    DROP
FORWARD  ACCEPT
OUTPUT   ACCEPT
```

This means:

- `INPUT DROP`: traffic addressed to Alpine-Lab-01 is denied unless explicitly permitted.
- `FORWARD ACCEPT`: routed traffic through Alpine-Lab-01 is currently unrestricted.
- `OUTPUT ACCEPT`: traffic generated by Alpine-Lab-01 is currently unrestricted.

The distinction between the three chains is fundamental:

```text
Traffic TO the router       -> INPUT
Traffic FROM the router     -> OUTPUT
Traffic THROUGH the router  -> FORWARD
```

Example:

```text
Alpine-02 -> SSH -> Alpine-01
                    |
                  INPUT
```

while:

```text
Alpine-02 -> Alpine-01 -> Internet
                    |
                  FORWARD
```


## 5. Stateful Firewall and conntrack

Linux Netfilter can track the state of network exchanges using connection tracking (`conntrack`).

Important states introduced during this phase:

```text
NEW
ESTABLISHED
RELATED
```

`NEW` represents traffic beginning a new tracked exchange.

`ESTABLISHED` represents subsequent traffic belonging to an exchange that Netfilter already recognizes.

`RELATED` represents traffic associated with an existing tracked connection.

The general rule:

```bash
-m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
```

allows traffic belonging to already recognized connections.

This is the basis of a **stateful firewall**.

## 6. ICMP and INPUT vs FORWARD

ICMP stands for **Internet Control Message Protocol**.

It is used for network control and diagnostic messages. `ping` uses ICMP Echo Request and Echo Reply.

Initially:

```bash
ping -c 3 10.10.10.1
```

from Alpine-Lab-02 failed.

However:

```bash
ping -c 3 8.8.8.8
```

worked.

This demonstrated the difference between `INPUT` and `FORWARD`.

Ping to the router:

```text
Alpine-02
    |
    | ICMP Echo Request
    v
10.10.10.1
    |
  INPUT
    |
  DROP
```

Ping through the router:

```text
Alpine-02
    |
    | ICMP Echo Request
    v
Alpine-01
    |
 FORWARD
    |
 ACCEPT
    v
8.8.8.8
```

An explicit rule was added for Echo Requests arriving from the trusted LAN:

```bash
-A INPUT -i eth1 -p icmp --icmp-type 8 -j ACCEPT
```

Afterward, pinging `10.10.10.1` worked successfully.

## 7. ICMP + conntrack Experiment

A temporary experiment was performed to observe connection tracking directly.

Two temporary rules were inserted before the generic `RELATED,ESTABLISHED` rule:

```text
ICMP echo-request + NEW          -> ACCEPT
ICMP echo-request + ESTABLISHED  -> ACCEPT
```

Then:

```bash
ping -c 3 10.10.10.1
```

was executed.

The counters showed:

```text
NEW           1 packet
ESTABLISHED   2 packets
```

This demonstrated that conntrack treated the first Echo Request as the beginning of the tracked exchange and subsequent requests as part of the established exchange.

The temporary diagnostic rules were removed afterward.

The permanent ICMP rule remains:

```bash
-A INPUT -i eth1 -p icmp --icmp-type 8 -j ACCEPT
```

## 8. DHCP Firewall Rule

DHCP stands for **Dynamic Host Configuration Protocol**.

It automatically provides network configuration such as:

- IP address
- Subnet mask
- Default gateway
- DNS server
- Lease information

In this lab, Alpine-Lab-01 provides DHCP through `dnsmasq`.

DHCP clients communicate primarily using UDP ports 67 and 68.

With `INPUT DROP`, DHCP initially failed because requests reached `eth1` but were dropped before `dnsmasq` could process them.

The following rule fixed the problem:

```bash
-A INPUT -i eth1 -p udp --dport 67 -j ACCEPT
```

This permits DHCP requests arriving from the isolated LAN.

## 9. DNS Firewall Rule

Alpine-Lab-01 also provides DNS through `dnsmasq`.

LAN clients use:

```text

```

DNS requests from clients therefore arrive at Alpine-Lab-01 and traverse `INPUT`.

UDP DNS was permitted with:

```bash
-A INPUT -i eth1 -p udp --dport 53 -j ACCEPT
```

This allowed Alpine-Lab-02 and Alpine-Lab-03 to use Alpine-Lab-01 as their DNS server.

Verified local DNS mappings included:

```text
alpine-lab-01 -> 10.10.10.1
alpine-lab-02 -> 10.10.10.2
```

## 10. Loopback Firewall Problem

A separate DNS issue occurred on Alpine-Lab-01 itself.

Its `/etc/resolv.conf` contained:

```text
search lab.local
nameserver 10.10.10.1
```

However:

```bash
nslookup alpine-lab-02
```

timed out.

A packet capture was performed:

```bash
sudo tcpdump -ni lo 'port 53'
```

It showed DNS requests such as:

```text
10.10.10.1:<client-port> -> 10.10.10.1:53
```

travelling through `lo`.

The existing DNS firewall rule only permitted packets arriving through `eth1`. Therefore local DNS traffic did not match the rule and eventually hit `INPUT DROP`.

The correct general solution was to permit loopback traffic:

```bash
-A INPUT -i lo -j ACCEPT
```

After adding this rule:

```bash
nslookup alpine-lab-02
```

worked correctly from Alpine-Lab-01.

This demonstrates why a default-deny host firewall normally needs an explicit loopback rule.

## 11. Local DNS / 127.0.0.1 Problem

Another name-resolution problem was discovered when Alpine-Lab-02 executed:

```bash
nslookup alpine-lab-01
```

and received:

```text
127.0.0.1
```

instead of:

```text
10.10.10.1
```

The cause was Alpine-Lab-01's `/etc/hosts`.

It contained:

```text
127.0.0.1 alpine-lab-01.my.domain alpine-lab-01 localhost.localdomain localhost
```

At the same time, `dnsmasq` was configured with:

```text
expand-hosts
```

As a result, the local hostname information was exposed through DNS.

This produced an important semantic problem for remote clients: `127.0.0.1` always means **this host**.

Therefore, when Alpine-Lab-02 resolved:

```text
alpine-lab-01 -> 127.0.0.1
```

and executed:

```bash
ssh airgon@alpine-lab-01
```

it actually connected back to Alpine-Lab-02 itself.

The problem was confirmed using:

```bash
ssh -v airgon@alpine-lab-01
```

which showed:

```text
Connecting to alpine-lab-01 [127.0.0.1] port 22.
```

## 12. Correcting Alpine-Lab-01 /etc/hosts

Alpine-Lab-01's `/etc/hosts` was changed so that loopback remained associated with localhost while the router hostname used its LAN address:

```text
127.0.0.1    localhost localhost.localdomain
10.10.10.1   alpine-lab-01.lab.local alpine-lab-01
::1          localhost localhost.localdomain
```

`dnsmasq` was then restarted.

Afterward, from Alpine-Lab-02:

```bash
nslookup alpine-lab-01
```

returned:

```text
Name:    alpine-lab-01.lab.local
Address: 10.10.10.1
```

and:

```bash
getent hosts alpine-lab-01
```

returned the correct `10.10.10.1` address.

DNS was therefore corrected.

## 13. SSH Host-Key Warning

After fixing DNS, SSH produced:

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

This occurred because the hostname `alpine-lab-01` had previously resolved incorrectly to `127.0.0.1`.

Alpine-Lab-02 had therefore associated the hostname with the wrong SSH host identity.

The incorrect hostname entries were removed:

```bash
ssh-keygen -R alpine-lab-01
ssh-keygen -R alpine-lab-01.lab.local
```

The new ED25519 fingerprint presented over the network was:

```text
SHA256:RgJxw2RXzvc2VMLjZrrxyfGCsH8ZQvBVtXsQIhCHV88
```

Instead of blindly accepting the key, the actual host key was verified directly on Alpine-Lab-01:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Result:

```text
256 SHA256:RgJxw2RXzvc2VMLjZrrxyfGCsH8ZQvBVtXsQIhCHV88 root@alpine-lab-01 (ED25519)
```

The fingerprints matched exactly.

This demonstrates an important SSH security principle:

> A changed SSH host key should not automatically be accepted. The new fingerprint should first be verified through a trusted path.

A later verbose SSH test confirmed successful hostname resolution, host-key verification, password authentication, PTY allocation, and interactive shell startup.

## 18. Key Lessons

### INPUT vs OUTPUT vs FORWARD

```text
Destination is the router:
    INPUT

Generated by the router:
    OUTPUT

Passing through the router:
    FORWARD
```

### Default-deny firewall

Using:

```text
INPUT DROP
```

means services must be explicitly permitted.

This exposed dependencies that were previously hidden:

```text
SSH       TCP/22
DHCP      UDP/67
DNS       UDP/53
ICMP      protocol-specific rule
loopback  lo
```

### Stateful filtering

`conntrack` allows the firewall to reason about traffic as part of an exchange rather than treating every packet independently.

```text
NEW
ESTABLISHED
RELATED
```

The ICMP experiment demonstrated this directly using packet counters.

### Interface restrictions

Rules such as:

```text
-i eth1
```

express a trust boundary.

Instead of saying:

> Allow DNS from everywhere.

the firewall can say:

> Allow DNS arriving from the trusted LAN interface.

### Loopback matters

A default-deny firewall must account for local communication through `lo`. Otherwise services on the machine may fail to communicate with each other.

### 127.0.0.1 is always local

A DNS server must not advertise another machine as `127.0.0.1`, because every client interprets that address as itself.

### SSH host-key warnings matter

A changed host key can indicate:

- A rebuilt server
- An IP/hostname reassignment
- Incorrect DNS
- A possible man-in-the-middle attack

The fingerprint should therefore be verified rather than blindly accepted.

## 19. Next Step — Stateful FORWARD Firewall

The remaining major weakness is:

```text
FORWARD ACCEPT
```

Currently, packets routed through Alpine-Lab-01 are accepted by default.

The next objective is to move toward:

```text
FORWARD DROP
```

with explicit stateful forwarding rules.

The intended model will be approximately:

```text
LAN -> WAN
NEW
        ACCEPT

LAN <- WAN
ESTABLISHED,RELATED
        ACCEPT

WAN -> LAN
NEW unsolicited traffic
        DROP
```

Conceptually:

```text
Alpine-Lab-02
10.10.10.2
      |
      | NEW
      v
Alpine-Lab-01
    FORWARD
      |
      +--------------> Internet
      |
      <--- ESTABLISHED,RELATED
      |
Internet --- NEW ---> X DROP
```

This will extend the same stateful-firewall principles already learned with `INPUT` to traffic travelling **through the router**.

Before beginning this change, the current configuration should be committed and snapshotted.
